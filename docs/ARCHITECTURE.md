# Архитектура

## Поток данных

1. **Профили** (`app/data/profiles.py`). CSV → `CompanyProfile`: продукты, ВЭД, отрасль, доли, контрагенты, `data_gaps`. Строятся один раз при старте и хранятся в SQLite.
2. **Чувствительность** (`app/data/sensitivity.py`). Признаки → веса факторов (noisy-OR, чтобы вес не рос без предела), знак влияния и текстовое обоснование для каждого вклада. Роль пользователя умножает веса.
3. **Новости** (`app/news`). Адаптеры источников (RSS/Atom, JSONL; `config/sources.yaml` с уровнем доверия) → фильтр шума (спорт, шоу-бизнес; для официальных источников не применяется) → дедуп в три уровня: хэш текста → MinHash по шинглам лида и перекрытие заголовков (окно 2 дня) → для пограничной похожести 0,2–0,3 короткий вопрос Gemma «одно ли это событие» → классификация → сюжет. Каждый проход пишет здоровье источника в `source_status`. Сбор идёт в фоне (APScheduler, первый проход сразу после старта) с фоновым приоритетом бюджета.
4. **Классификация.** Сначала правила (ключевые слова с границей слова, направление по фрагменту предложения) и сущности (`app/news/entities.py`: регионы РФ, отрасли → класс ОКВЭД, даты вступления в силу). Gemma 4 вызывается, только если правила нашли бизнес-факторы или источник официальный; её JSON дополняет сущности, но не может их испортить (регионы — только из справочника, даты — только ISO). Факты и прогнозы разделяются, числа извлекаются.
5. **Сюжеты** (`app/news/stories.py`). Событие = одна новость в пересказах; сюжет = цепочка событий за 45 дней с общим главным фактором и лексической близостью (решение ЦБ → ОФЗ → прогнозы аналитиков). Лента показывает сюжет одной карточкой с таймлайном.
6. **Ранжирование** (`app/ranking/scorer.py`). `Σ вес_фактора × уверенность × (0,7 для новости о чужой отрасли) + совпадение стран ВЭД + отрасль компании/контрагентов + регион компании/контрагентов + важность` × свежесть (период полураспада 14 дней). Регион — только усилитель: «Москва» в тексте сама по себе не делает новость деловой. Ослабление ×0,5 для новости о чужой отрасли действует только на отраслевые факторы, макроканалы (ставка, курс, инфляция, кредитование…) — на всех. Персональные поправки (`app/ranking/personal.py`, таблица `profile_overrides`): 👎 «не про мой бизнес» ×0,6, 👍 ×1,2, ручные «важнее» ×1,6 и «не показывать» ×0. Затем сюжет сворачивается в карточку, а MMR (λ = 0,3) не даёт поставить подряд карточки с одним главным фактором. Эффект: риск / возможность / смешанный / отслеживать. Все слагаемые сохраняются как причины.
   **LLM-реранк** (`app/ranking/rerank.py`, `/api/feed/rerank`): Gemma оценивает топ-15 карточек 0–3 с причиной; итог 0,6 × базовый скор + 0,4 × оценка. Фронтенд показывает ленту сразу и переставляет карточки, когда приходит ответ.
7. **Агент** (`app/agent/orchestrator.py`) — для события, открытого пользователем.

## Граф компаний (этап 3)

`app/data/graph.py` при сборке профилей считает по 1,38 млн платежей и связям физлиц:
- **отраслевой профиль контрагентов** — доли входящих/исходящих платежей по классам ОКВЭД (по всем
  контрагентам; платежи с компаниями вне выборки — отдельная доля «отрасль неизвестна»);
- **концентрацию** (индекс Херфиндаля–Хиршмана) покупателей и поставщиков, их число;
- **PageRank** в сети денежных потоков (numpy, без внешних графовых библиотек) — перцентиль «узловости»;
- **аффилированность** — компании, связанные через общих физлиц (физлица с > 25 компаниями отбрасываются как шум);
- **географию** контрагентов.

Матрица чувствительности добавляет **эффекты второго порядка**: если ≥ 15% платежей покупателей/поставщиков
приходится на отрасль, чувствительную к фактору, компания получает ослабленную чувствительность с причиной
`graph:<in|out>:<ОКВЭД>`. `app/data/peers.py` строит **группы похожих компаний** (ОКВЭД 4 знака + полоса
выручки, иначе шире) — бенчмарк продуктов и «холодный старт» (причина `peers:<продукт>`) для профилей без сигналов.

## Двухуровневая генерация (экономия бюджета 500 ₽/день)

1. **Уровень события** (`app/agent/event_brief.py`, DeepSeek-V4.1-Flash): один раз на событие — ключевые факты с источниками,
   прогнозы, даты вступления в силу, каналы влияния (фактор → механизм → кто выигрывает/проигрывает → горизонт),
   сверка с тезисами банка (`agrees | contradicts | context`). Кэш — таблица `event_briefs`.
2. **Уровень клиента** (DeepSeek-V4.1-Flash): персональный инсайт получает разбор события вместо полных текстов новостей
   (тексты обрезаются до 600 символов) — промпт в несколько раз короче.

Все ответы моделей валидируются pydantic-схемами (`app/agent/llm_schemas.py`); невалидный ответ модель
исправляет сама по тексту ошибки (одна попытка, отмечается в трассировке как `repaired`).

## Режимы LLM и бюджет

`LLM_MODE=auto|live|replay|mock`. Бюджет считается по московским суткам (лимит организаторов сбрасывается в 03:00 МСК):
до 60% — все задачи; 60–80% — фоновый предрасчёт останавливается (резерв под пользователей); 80–100% — запасные модели;
100% — детерминированный режим. Повторы при 429/5xx с учётом `Retry-After`.

## Цикл агента

```mermaid
sequenceDiagram
  participant O as Оркестратор
  participant L as LLM (разрешённые)
  participant T as Инструменты (allowlist)
  participant C as Критик (правила + LLM)
  O->>O: relevance (скоринг, причины)
  O-->>O: preview: главный вывод и сценарии правилами → сразу в UI (SSE)
  O->>L: plan (Qwen) → шаги и гипотеза
  loop шаги плана (≤14 вызовов)
    O->>T: get_event_brief / get_company_profile / get_bank_theses / get_bank_forecast / scenario_calc / get_story_timeline / get_regulation_dates / search_bank_analytics / get_counterparties / get_peer_benchmark / get_playbook / search_related_news / check_consistency
    T-->>O: результат → ctx.memory (общий контекст)
  end
  O->>L: draft (DeepSeek) → Insight JSON
  O->>C: правила: 6 вопросов, источники, валидность id, позиция банка, персонализация, числа, injection
  O->>L: самопроверка (DeepSeek; независимые судьи — GLM и Kimi)
  alt есть замечания
    O->>T: повторный поиск по аналитике (если нет позиции банка)
    O->>L: revise (DeepSeek)
    O->>O: repair: удалить неподтверждённое, понизить «факт» до «предположения»
  end
  O->>O: finalize: SourceRef для каждого id, трассировка
```

Если LLM недоступна (mock-режим, исчерпан бюджет, сетевая ошибка), каждый шаг переходит на детерминированную реализацию (`app/agent/rules.py`). Шаблоны последствий и действий берутся из `config/playbook.yaml`. Тот же плейбук передаётся LLM как подсказка. Ограничители на один запрос: 90 секунд и 4 ₽; при превышении в трассировке появляется шаг `limit`, а оставшиеся шаги идут правилами.

**Сценарии и «что если»** (`app/agent/scenario.py`). Суммы в рублях модель не придумывает: их считает калькулятор по прозрачным формулам (ставка: −долг × доля под плавающей ставкой × Δ + депозиты × Δ; курс: −импорт × Δ × (1 − перенос в цены) + экспорт × Δ; зарплаты: −ФОТ × (рост − заложенный рост)). Базовый сценарий — прогноз Альфа-Банка на 12 месяцев (средняя ставка 2027 г., курс, номинальные зарплаты), негативный и позитивный — сдвиги от него. Параметры компании по умолчанию оцениваются по профилю (долг ≈ 25% выручки при наличии кредита, импорт ≈ 30% выручки при ВЭД, ФОТ по численности) и подписаны как оценки; пользователь вводит свои суммы в блоке «Что если» (`POST /api/scenario`). «Что может изменить вывод» — триггеры с числами прогноза банка как точкой отсчёта.

**Честный денежный эффект (23.10, версия калькулятора 3).** Сумма в рублях — серьёзное утверждение. Поэтому калькулятор осторожен:
- **Базовый сценарий — прогноз Альфа-Банка, и это 0 к плану.** Считаем, что ставка, курс и зарплаты по прогнозу банка и текущая динамика рынков уже заложены в план компании. Новость сама по себе план не меняет.
- **Негативный и позитивный сценарии — умеренные отклонения от прогноза, а не катастрофы:** ставка ±1 п.п., курс на 10% слабее или на 5% крепче, зарплаты +3/−2 п.п.
- **В расчёт идут только рычаги, которые двигает само событие.** Это его главные факторы с понятным направлением и связью через профиль. Рычага «ставка по умолчанию» больше нет.
- **Отраслевой рычаг (выручка или закупки) появляется только при четырёх условиях сразу:**
  - в новости есть число изменения: «продажи −5%», «бензин +26%»;
  - эффект однозначен — риск или возможность;
  - связь прямая: своя отрасль или контрагенты с долей от 20%;
  - событие касается региона компании или её контрагентов.
- **Сила переноса консервативна:** своя отрасль — половина изменения рынка, через покупателей — четверть. Потолок — 1,5% выручки.
- **Если эффект меньше 150 тыс. ₽ и 0,05% выручки, суммы не показываются.** Вместо них пишем «заметного влияния на прибыль не ожидаем». Если модель после разбора оценила связь как слабую, суммы тоже не показываем.

Пример, из-за которого всё переделано. Новость «в Югре расселили 1,1 млн кв. м аварийного жилья» раньше давала московскому девелоперу +8,1 млн ₽ в базе: срабатывал типовой шок «спрос +5%». Теперь эффекта нет по трём причинам: регион чужой, числа изменения рынка нет, а новость описывает уже случившееся.

**«Деньги на кону» на главной** (`GET /api/money`) — возможный плюс, возможный минус и минус, который можно ограничить инструментами банка (фиксация ставки, хедж курса, фиксация цен поставщиков). Новости не суммируются: у разных новостей одна причина, например ставка, и это один риск. Поэтому для каждого рычага берётся самый сильный минус и плюс среди новостей средней и высокой важности, затем рычаги складываются.

**Единая важность новости (0–3).** Пороги по профилю откалиброваны на размеченном наборе из 159 пар: оценка от 1,0 — все события размечены как критичные, 0,6–1,0 — почти все релевантные. Оценка модели после полного разбора главнее, но поднять важность она может не больше чем на ступень выше профиля, а понизить — всегда. Быстрая оценка по заголовку работает так же. На карточке одна шкала с подписью и источником оценки. Сортировка «По важности» идёт строго по ней, «Рекомендуемые» — порядок сервиса с разнообразием тем.

**Человеческий текст (`app/agent/humanize.py`).** Модель ссылается на источники id вида `graph:in:71` или `profile:CL_PRODUCT_LOA_MARK`. Эти ссылки остаются в `sources` каждого утверждения, а в интерфейсе показываются метками «контрагенты», «профиль», «банк». Из текста для клиента id, коды продуктов, факторов и названия служебных полей убираются или заменяются словами. Это делается при сохранении и при чтении разбора, поэтому старые разборы в снапшоте тоже чистые. В промпте есть правило не писать id в текст.

## JSON-схема инсайта (`app/agent/schemas.py`)

```json
{
  "headline": "...",
  "takeaway": {"text": "главный вывод для компании", "kind": "ai_inference", "sources": ["profile:CL_PRODUCT_LOA_MARK", "news:seed-01", "bank:t01"]},
  "what_happened": [{"text": "...", "kind": "fact|assumption", "sources": ["news:..."]}],
  "why_it_matters": [{"text": "...", "kind": "ai_inference", "sources": ["profile:...", "graph:in:41.20"]}],
  "consequences": {"risks": [], "opportunities": [], "drivers": []},
  "actions": [{"text": "...", "action_type": "finance|hedge|analysis|operations|monitor|question"}],
  "bank_view": [{"text": "...", "kind": "bank_view", "sources": ["bank:t01"]}],
  "products": [{"product": "...", "why": "...", "label": "Предложение Альфа-Банка"}],
  "sources": [{"id": "bank:t01", "type": "bank", "title": "...", "date": "...", "page": 1, "quote": "...", "stale": false}],
  "relevance": {"score": 0.44, "reasons": [], "consistency_issues": []},
  "quality": [{"name": "Числа в фактах есть в источниках", "passed": true}],
  "trace_id": "tr-..."
}
```

Пространства id источников: `news:<id>` — новость; `bank:<thesis_id|chunk_id>` — аналитика банка; `profile:<признак>` — признак компании; `graph:<in|out>:<ОКВЭД>` — контрагент из графа платежей.

## Модель данных (SQLite → PostgreSQL)

| Таблица | Назначение |
|---|---|
| `companies` | Профиль компании (JSON) |
| `user_links` | Физлицо ↔ компания (RBAC) |
| `news`, `events` | Новости (с MinHash-сигнатурой) и события (склейка, классификация, сюжет) |
| `stories` | Сюжеты: цепочки связанных событий |
| `profile_overrides` | Персональные поправки к весам факторов: из обратной связи или ручные |
| `source_status` | Здоровье источников: последний опрос, ошибки, сколько новостей и шума |
| `insights` | Кэш инсайтов по ключу `event|company|role` |
| `trace_steps` | Трассировка агента |
| `llm_cache`, `llm_usage` | Кэш ответов LLM, расход по дням и моделям |
| `feedback`, `audit_log` | Обратная связь, журнал доступа |

## Масштабирование и сопровождение (критерий 07)

- **Новая отрасль или продукт:** строка в `config/sensitivity.yaml` и при необходимости фактор в `config/factors.yaml` и `config/playbook.yaml`. Код не меняется.
- **Новый источник:** запись в `config/sources.yaml`; для нового формата — класс-адаптер в `app/news/sources.py`.
- **Новые аналитические материалы банка:** положить PDF → `extract_bank_theses.py` → проверить `bank_theses.auto.json` → перенести в `bank_theses.json`. Материалы старше года автоматически помечаются как устаревшие.
- **Нагрузка:** события классифицируются один раз и разделяются между клиентами; дорогой персональный шаг (агент) запускается только при открытии карточки и кэшируется. Для продакшена: PostgreSQL + pgvector, очередь задач для ingest, предрасчёт инсайтов для топ-событий.
- **Качество:** промпты версионируются (`PROMPT_VERSION` попадает в трассировку); регрессионный прогон `scripts/evaluate.py` на размеченном наборе перед каждым изменением промптов или весов.
